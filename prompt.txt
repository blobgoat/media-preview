# Palantir PNG Icon Display Widget — Implementation Specification

## Objective

Implement a small Palantir Foundry custom widget in the existing `media-preview` repository.

The widget accepts a single string parameter:

```tsiconName: string```

It uses that value to look up a PNG icon in a **new repository-local icon registry**, then renders the matching PNG centered inside a flex container.

There are currently **no icon PNGs and no icon registry in the repository**.

This task is therefore primarily about creating the infrastructure/wiring so PNG icons can be added later without changing the widget rendering logic.

The intended future flow is:

```textPalantir iconName parameter          ↓new repository-local icon registry          ↓PNG asset path          ↓<img>          ↓centered flex container```

Do **not** use `@radix-ui/react-icons` or another third-party icon library as the icon source.

The icons for this widget will eventually be repository-owned PNG files supplied separately after this implementation.

---

# 1. Inspect the Existing Repository First

Before modifying code, inspect the current `media-preview` repository and preserve its existing Palantir widget architecture.

At minimum, inspect:

* `src/Widget.tsx`* `src/main.config.ts`* `src/main.css`* `src/context.ts`* `src/client.ts`* `src/components/ExampleCard.tsx`* `src/__tests__/Widget.test.tsx`* `package.json`* TypeScript configuration* Vite configuration* Vitest/test configuration

Use the repository's existing React, TypeScript, Vite, Vitest, and `@osdk/widget.client` setup.

Do not replace the existing scaffold or introduce a new application architecture.

---

# 2. Important Starting-State Requirement

The repository currently contains:

* no icon PNG collection,* no icon registry,* no icon-name mapping,* no established repository icon naming convention.

Do not search for or assume that an icon registry already exists.

Instead, create the minimal infrastructure needed to support one.

The implementation must work correctly even while the registry contains **zero icons**.

---

# 3. Widget Parameter

Add a widget parameter named:

```tsiconName```

with the TypeScript/runtime meaning:

```tsstring```

Wire it through the existing Palantir widget configuration system in `src/main.config.ts` using the same conventions already used by the repository.

Do not add:

* icon size parameters,* color parameters,* alignment parameters,* file-upload parameters,* icon picker parameters,* URL parameters,* fallback-icon parameters.

This task has exactly one configurable widget value:

```texticonName```

---

# 4. No Default Icon

`iconName` should not have a semantic default icon.

If no value is supplied, the widget should simply display an empty flex container.

The following values should all result in no icon being displayed:

```tsundefinednull""```

Handle whatever subset of those values can actually reach the widget through the existing Palantir parameter API.

Do not automatically display:

* a question mark,* an error icon,* an Add icon,* a placeholder icon,* a Radix icon,* or another arbitrary fallback image.

---

# 5. Create the PNG Asset Directory

Create a clear repository-owned location for future PNG icon files.

Preferred structure:

```textsrc/  assets/    icons/      index.ts```

There do not need to be any PNG files in the directory as part of this task.

Do not generate fake production PNG icons merely to populate the directory.

The user will add the actual PNG icon files later.

---

# 6. Create the Icon Registry

Create a registry in:

```textsrc/assets/icons/index.ts```

The registry should map a string icon name to the imported PNG URL/path that React/Vite can use as an `<img src>` value.

Conceptually, the eventual structure should support entries like:

```tsimport searchIcon from "./search.png";import calendarIcon from "./calendar.png";

export const iconAssets = {    search: searchIcon,    calendar: calendarIcon,};```

However, because the PNG files do not exist yet, the production registry created by this task should initially be empty.

For example:

```tsexport const iconAssets: Record<string, string> = {};```

An equivalent strongly typed implementation is acceptable.

The important requirement is that future PNG icons can be added by:

1. placing the `.png` file in `src/assets/icons/`,2. importing it in `src/assets/icons/index.ts`,3. adding one name-to-PNG entry to `iconAssets`.

Adding a new PNG should **not require editing `Widget.tsx` or the icon display component**.

---

# 7. PNGs Must Be the Intended Asset Type

This registry is specifically infrastructure for PNG icon assets.

Do not implement the registry around:

* React icon components,* SVG component libraries,* Radix icons,* Base64 strings,* remote URLs,* CSS icon fonts.

The future production assets will be local `.png` files.

Use the normal Vite static asset import mechanism already supported by the repository.

---

# 8. Do Not Automatically Scan the Filesystem

Do not add filesystem scanning, runtime directory discovery, or complicated dynamic loading.

A simple explicit registry is preferred.

For example, once actual assets exist:

```tsimport search from "./search.png";

export const iconAssets = {    search,};```

is preferable to introducing unnecessary dynamic import infrastructure.

The registry should remain easy for a developer to read and edit manually.

---

# 9. Icon Lookup

Create straightforward lookup behavior.

Conceptually:

```tsconst iconSrc = iconAssets[iconName];```

The implementation must safely handle names that do not exist.

For example:

```tsfunction getIconAsset(iconName?: string): string | undefined {    if (!iconName) {        return undefined;    }

    return iconAssets[iconName];}```

The exact helper structure may vary, but the observable behavior must match this specification.

---

# 10. Invalid Icon Names

If the widget receives:

```tsiconName = "does-not-exist"```

and that key is absent from `iconAssets`:

* do not throw,* do not crash,* do not show a broken `<img>`,* do not show browser missing-image UI,* do not substitute another icon.

Simply render no `<img>` element.

The surrounding flex container should remain rendered.

---

# 11. Widget Rendering

The widget should render one main flex container.

Conceptually:

```tsx<div className="icon-widget">    {iconSrc ? (        <img src={iconSrc} aria-hidden="true" />    ) : null}</div>```

Adapt the implementation to the repository's existing structure.

Do not copy this code blindly if the existing scaffold requires a slightly different component arrangement.

---

# 12. Flex Container Contract

The main widget container must:

```cssdisplay: flex;align-items: center;justify-content: center;width: 100%;height: 100%;box-sizing: border-box;overflow: hidden;```

This is the required layout contract.

The purpose is to keep the icon centered horizontally and vertically inside whatever dimensions the Palantir widget host provides.

Equivalent CSS that provides exactly the same behavior is acceptable.

---

# 13. PNG Rendering Contract

When a valid registry entry exists, render it using an HTML `<img>` element.

The image should remain contained within the available widget area rather than forcing the widget to overflow.

Use:

```cssmax-width: 100%;max-height: 100%;object-fit: contain;```

or equivalent behavior.

Do not stretch the PNG disproportionately.

Do not crop the PNG.

Do not use the PNG as a CSS background image.

The rendered asset should be an actual `<img>` element.

---

# 14. No Fixed Widget Dimensions

Do not set a fixed width or height for the widget container.

Avoid behavior such as:

```csswidth: 100px;height: 100px;```

The outer widget should inherit the available dimensions supplied by the host.

The PNG should stay centered as those dimensions change.

---

# 15. No Production Placeholder PNG

Do not add a fake icon solely so the production registry has an entry.

The production registry may correctly ship as:

```ts{}```

until the actual PNG assets are supplied later.

This empty-registry state is intentional.

---

# 16. Testing an Empty Production Registry

Because there are no real PNG assets yet, tests should **not require adding a production PNG file**.

Tests that need to verify successful icon rendering should mock the icon registry or otherwise provide a test-only registry value using the repository's existing Vitest capabilities.

For example, a test may mock:

```tssrc/assets/icons/index.ts```

so that the registry behaves conceptually like:

```ts{    search: "/mock/search.png"}```

The exact mocking implementation should follow the existing Vitest setup.

Do not add fake production icons simply to make the test pass.

---

```ts{    search: "/mock/search.png"}```

render the widget with:

```tsiconName = "search"```

Verify that:

1. an `<img>` element is rendered,2. its `src` corresponds to the registered asset,3. only the requested asset is displayed.

Using a mocked registry equivalent to:

```ts{    search: "/mock/search.png",    calendar: "/mock/calendar.png"}```

For example:

```textsearch → /mock/search.pngcalendar → /mock/calendar.png```

This confirms that the widget is actually driven by `iconName` rather than containing a hardcoded image.

# 23. Required Test — Image Containment

# 24. Accessibility

Treat these icons as decorative for this implementation.

The rendered `<img>` should therefore not use `iconName` as visible or screen-reader content.

Use an appropriate decorative-image pattern, such as:

```tsxalt=""```

and/or the equivalent accessibility behavior appropriate for an `<img>`.

Do not expose an internal identifier such as:

```textemployee_search_16```

as meaningful alternate text.

Do not add an accessibility-label parameter as part of this task.

---

# 25. Remove Unneeded Scaffold UI From the Final Widget

The repository currently contains example/scaffold presentation code such as `ExampleCard.tsx`.

If the existing `Widget.tsx` currently renders scaffold/example content instead of the requested widget, replace that rendered example UI with the icon display behavior.

Do not leave unrelated example content visible alongside the icon.

However, do not delete unrelated scaffold files unless they are genuinely no longer referenced and removing them is safe.

The important observable requirement is that the resulting widget UI contains only the icon display area.

# 26. Do Not Use Radix Icons

Although `package.json` contains icon-related third-party dependencies such as:

# 27. No Runtime Network Requests

All future icon assets are local repository assets.

The widget must not:

* fetch PNGs from an API,* construct remote URLs,* call a server based on `iconName`,* download an image at runtime.

Resolving an icon must remain a synchronous local lookup.

# 28. No Additional Interaction

Do not add:

# 29. No Additional Visual UI

* a visible card,* visible border,* icon-name label,* title,* error text,* loading indicator,* placeholder graphic,* background decoration,* empty-state message.

```textwidget bounds└── centered flex container    └── optional PNG image```

When no PNG resolves, only the container remains.

# 30. Expected Repository Architecture

A reasonable final structure is:

```textsrc/  assets/    icons/      index.ts  components/    IconDisplay.tsx  Widget.tsx  main.config.ts  main.css```

The dedicated `IconDisplay.tsx` component is optional if the implementation remains clearer inside `Widget.tsx`.

```textwidget parameter    ↓registry lookup    ↓PNG rendering```

# 31. Future PNG Addition Workflow

The implementation must make the following future operation possible without changing the widget component.

Suppose the user later adds:

```textsrc/assets/icons/search.pngsrc/assets/icons/calendar.pngsrc/assets/icons/settings.png```

They should only need to update the registry approximately like:

```tsimport search from "./search.png";import calendar from "./calendar.png";import settings from "./settings.png";

export const iconAssets = {    search,    calendar,    settings,};```

After that:

```texticonName = "search"```

should render `search.png`.

```texticonName = "calendar"```

should render `calendar.png`.

```texticonName = "settings"```

should render `settings.png`.

No change to the lookup/rendering component should be necessary.

This future workflow is one of the primary acceptance criteria for the architecture.

# 35. Final Intended Behavior

Immediately after this task, the production state may be:

```tsexport const iconAssets: Record<string, string> = {};```

Therefore:

```texticonName = "search"```

currently renders nothing because `search.png` has not been supplied yet.

That is correct.

Later, after the user adds:

```textsrc/assets/icons/search.png```

and updates the registry:

```tsimport search from "./search.png";

export const iconAssets = {    search,};```

the exact same widget should automatically behave as:

```texticonName = "search"        ↓iconAssets["search"]        ↓search.png        ↓<img src={search}>        ↓centered flex container```

The widget code itself should not need to change.

That separation between **icon infrastructure** and the **future PNG collection** is the central architectural requirement of this task.
